# 영화 박스오피스 인사이트 대시보드 구현 계획서

## 1. 문서 목적과 적용 기준

이 문서는 `PRD.md`, `ARCHITECTURE.md`, `AGENTS.md`, `ERD.md`와 현재 fixture 기반 demo 구현을 실제 KOBIS·Supabase 연동 서비스로 확장하기 위한 실행 기준이다. 사용자 기능과 인수 여부는 PRD, 기술 선택과 요청 흐름은 ARCHITECTURE, 데이터 구조는 ERD, 보안·검증 규칙은 AGENTS를 우선한다. 문서 사이에 충돌이 생기면 임의로 구현하지 않고 영향과 적용 기준을 먼저 보고한다.

현재 구현은 `DATA_MODE=demo`에서 목록 화면과 상태 표현을 검증하는 프로토타입이다. 이 문서에서 말하는 완료는 별도 표시가 없는 한 `DATA_MODE=live`에서도 실제 KOBIS와 Supabase를 통해 동작하고 관련 자동 검사가 통과한 상태를 뜻한다.

## 2. 화면 상태

목록과 인사이트는 이전 조건의 결과를 새 조건의 결과처럼 보여주지 않는다. 요청 조건이 바뀌면 진행 중인 요청을 취소하거나 응답 세대를 비교해 마지막 요청만 반영한다.

| 상태 | 진입 조건 | 화면 처리 | 가능한 사용자 행동 |
| --- | --- | --- | --- |
| 초기 | 화면에 처음 진입했지만 요청을 시작하기 전 | 기본값을 한국 시간 기준 전일·일간으로 설정한다. demo에서는 샘플 확인을 위해 별도 기본일을 사용할 수 있음을 표시한다. | 날짜·기간 유형 변경 |
| 로딩 | 최초 조회, 조건 변경 또는 재시도 요청이 진행 중 | 로딩 표시를 제공하고 이전 조건의 표·집계를 현재 결과처럼 표시하지 않는다. | 조건 변경 또는 요청 취소를 유발하는 새 조회 |
| 성공 | 원본 결과가 한 건 이상이고 요청·검증·저장본 대조가 완료됨 | 조회 조건, 실제 집계 범위, 데이터 보유 상태와 결과를 표시한다. | 날짜·기간·검색어·분석 옵션 변경 |
| 정상 빈 결과 | 외부 응답의 예상 결과 배열이 실제로 비어 있고 정상 빈 결과로 저장·확인됨 | “해당 조건의 박스오피스 데이터가 없습니다”와 날짜·기간 변경 안내를 표시한다. 오류나 검색 결과 없음으로 표현하지 않는다. | 날짜·기간 변경 |
| 검색 결과 없음 | 원본 목록은 있으나 현재 검색어와 일치하는 영화가 없음 | 검색 전용 안내와 검색어 지우기를 제공한다. 서버의 정상 빈 응답으로 취급하지 않는다. | 검색어 지우기·수정 |
| 오류 | 입력 이외의 DB·외부 API·응답 검증·저장 과정이 실패함 | 안전한 서비스 오류 코드와 안내를 표시하고, 재시도 가능한 오류에는 같은 조건 재시도를 제공한다. 원문 오류와 인증 정보는 표시하지 않는다. | 재시도·조건 변경 |
| 입력 오류 | 날짜·기간 유형·분석 일수·Top 값이 허용 범위를 벗어남 | 해당 입력을 교정할 수 있는 안내를 표시한다. | 입력 수정 |
| 인사이트 일부 날짜 실패 | 분석 기간 중 한 날짜라도 확보하지 못함 | 부분 합계나 Top을 완성 결과로 표시하지 않고 전체 분석 실패와 재시도를 표시한다. | 재시도·기간 축소 |
| 인사이트 전체 빈 결과 | 분석 기간의 모든 날짜가 정상 빈 응답 | 데이터 없음 상태와 데이터 보유 일수 `0일`을 표시한다. | 종료일·기간 변경 |

인사이트에서 일부 날짜가 정상 빈 응답인 것은 오류가 아니다. 해당 날짜는 차트 공백으로 표시하고 합계 및 일평균의 분모에서 제외하며, 전체 분석 기간과 실제 데이터 보유 일수를 함께 표시한다.

| 서버 내부 API | 입력 검증, 기본 날짜 계산, KOBIS 요청, 본문 오류와 스키마 검증, 숫자 정규화, 캐시 조회·갱신, DB 저장본 대조, 인사이트 계산, 안전한 DTO와 HTTP 상태 반환, 타임아웃·동시성 제한 | 비밀값을 응답·URL 로그에 노출, 외부 오류를 정상 빈 결과로 변환, 만료 캐시를 최신 결과처럼 반환 |
| 데이터베이스 | 영화·조회 기간·기간별 실적 저장, PK·FK·고유 제약으로 중복 방지, 트랜잭션 원자성, 캐시 생성·만료 시각 보존, JOIN 조회 | KOBIS 호출, 화면 검색 상태 관리, 브라우저 공개 역할의 직접 읽기·쓰기 허용 |
| KOBIS | 일간·주간·주말 박스오피스 원본 제공 | 서비스 내부 캐시 정책, 인사이트 집계, 사용자 화면 상태 결정 |

`KOBIS_API_KEY`와 `SUPABASE_SECRET_KEY`는 `server-only` 경계 안에서만 사용한다. 브라우저는 내부 API만 호출하며, Supabase 테이블에 직접 접근하지 않는다.

## 4. 내부 API 계약

### 4.1 한 줄 정의

- `GET /api/box-office?date=YYYY-MM-DD&type=daily|weekly|weekend` — 선택 기준일과 기간 유형의 박스오피스 목록을 반환한다.
- `GET /api/insights?endDate=YYYY-MM-DD&days=7|14|30&top=5|10` — 종료일을 포함한 일간 데이터로 매출·관객 추이, Top 영화와 보조 지표를 반환한다.

영화명 검색은 서버 재조회 없이 현재 목록에만 적용하므로 목록 API 파라미터에 포함하지 않는다.

### 4.2 요청 파라미터

| API | 파라미터 | 필수 | 허용값·기본값 | 검증 |
| --- | --- | --- | --- | --- |
| `/api/box-office` | `date` | 선택 | 생략 시 한국 시간 기준 전일 | 실제 존재하는 `YYYY-MM-DD`, 미래 날짜 금지 |
| `/api/box-office` | `type` | 선택 | `daily`, `weekly`, `weekend`; 기본 `daily` | 열거형 외 값 금지 |
| `/api/insights` | `endDate` | 선택 | 생략 시 한국 시간 기준 전일 | 실제 존재하는 `YYYY-MM-DD`, 미래 날짜 금지 |
| `/api/insights` | `days` | 선택 | `7`, `14`, `30`; 기본 `7` | 허용 목록 외 값 금지 |
| `/api/insights` | `top` | 선택 | `5`, `10`; 기본 `5` | 허용 목록 외 값 금지 |

### 4.3 성공 응답

모든 금액·인원 값은 JSON에서 정확한 10진 정수 문자열로 전달한다. `rank`만 검증 후 안전한 `number`로 전달하고, 누락된 개봉일은 `null`로 전달한다.

#### 목록 응답

```json
{
  "data": {
    "items": [
      {
        "movieCd": "string",
        "movieNm": "string",
        "rank": 1,
        "openDt": "YYYY-MM-DD|null",
        "salesAmt": "0",
        "audiCnt": "0",
        "salesAcc": "0",
        "audiAcc": "0"
      }
    ]
  },
  "meta": {
    "status": "ok|empty",
    "queryDate": "YYYY-MM-DD",
    "type": "daily|weekly|weekend",
    "rangeStart": "YYYY-MM-DD",
    "rangeEnd": "YYYY-MM-DD",
    "source": "fixture|cache|kobis",
    "collectedAt": "ISO-8601",
    "cachedAt": "ISO-8601|null",
    "expiresAt": "ISO-8601"
  }
}
```

#### 인사이트 응답

```json
{
  "data": {
    "timeline": [
      {
        "date": "YYYY-MM-DD",
        "status": "ok|empty",
        "salesAmt": "0|null",
        "audiCnt": "0|null"
      }
    ],
    "topBySales": [],
    "topByAudience": [],
    "summary": {
      "totalSalesAmt": "0",
      "totalAudiCnt": "0",
      "averageSalesAmt": "0",
      "averageAudiCnt": "0",
      "availableDays": 0
    }
  },
  "meta": {
    "status": "ok|empty",
    "endDate": "YYYY-MM-DD",
    "rangeStart": "YYYY-MM-DD",
    "rangeEnd": "YYYY-MM-DD",
    "days": 7,
    "top": 5,
    "requestedDays": 7,
    "availableDays": 0
  }
}
```

`topBySales`와 `topByAudience`의 항목은 `movieCd`, `movieNm`, 기간 합계와 순위를 가진다. 날짜별 누적 매출·누적 관객은 기간 합계에 더하지 않는다. Top 정렬은 합계 내림차순 후 `movieCd` 오름차순으로 고정한다.

### 4.4 실패 응답과 HTTP 코드

실패 응답은 `{ "error": { "code": "서비스 코드", "message": "안전한 안내", "retryable": true } }` 형식을 사용한다.

| HTTP | 상황 | 예시 서비스 코드 | 처리 원칙 |
| --- | --- | --- | --- |
| `400` | 잘못된 날짜, 미래 날짜, 허용되지 않은 기간·일수·Top 값 | `INVALID_REQUEST` | 외부·DB 호출 없이 종료, 입력 교정 안내 |
| `502` | KOBIS 네트워크 오류, 본문 오류, 스키마·필수 숫자 검증 실패 | `UPSTREAM_ERROR`, `UPSTREAM_INVALID_RESPONSE` | 오류를 캐시하지 않고 같은 조건 재시도 제공 |
| `504` | KOBIS 제한 시간 초과 | `UPSTREAM_TIMEOUT` | 요청을 중단하고 오류를 캐시하지 않음 |
| `503` | DB 조회·트랜잭션 저장·저장본 대조 실패 | `CACHE_READ_ERROR`, `CACHE_WRITE_ERROR`, `CACHE_VERIFY_ERROR` | 캐시 미스와 구분하고 불완전한 결과를 성공으로 반환하지 않음 |
| `500` | 분류되지 않은 서버 내부 오류 또는 서버 설정 오류 | `INTERNAL_ERROR`, `SERVER_MISCONFIGURED` | 비밀값·원문 오류 없이 일반 안내, 서버 로그도 민감정보 제거 |
| `501` | 개발 중 `DATA_MODE=live`가 아직 구현되지 않은 경우에만 사용 | `LIVE_MODE_NOT_IMPLEMENTED` | 구현 완료 후 제거하며 운영 환경에서는 발생하지 않아야 함 |

정상 빈 결과는 `200`과 `meta.status="empty"`로 반환한다. 검색 결과 없음은 클라이언트 상태이므로 별도 HTTP 오류가 아니다.

## 5. 요청 처리 순서와 실패 정책

### 5.1 공통 처리 흐름

`입력 검증 → 캐시 조회 → 외부 호출 → 검증·정규화 → 트랜잭션 저장 → 저장본 대조 → DTO 응답`

| 단계 | 정상 처리 | 실패 처리 |
| --- | --- | --- |
| 1. 입력 검증 | 날짜의 실제 유효성·미래 여부와 열거형을 검증하고 기본값을 확정한다. | `400`; 이후 단계는 실행하지 않는다. |
| 2. 캐시 조회 | 기간 유형+기준일로 조회하고 만료 시각을 서버 시각과 비교한다. 유효하면 JOIN 결과를 반환한다. | 조회 실패는 미스로 바꾸지 않고 `503`. 미스·만료만 외부 호출로 진행한다. |
| 3. 외부 호출 | KOBIS에 서버에서만 요청한다. 주간·주말의 실제 집계 범위는 응답에서 얻는다. | 네트워크·본문·스키마 오류는 `502`, 제한 시간 초과는 `504`. 기존 만료 캐시를 최신 결과처럼 반환하지 않는다. |
| 4. 검증·정규화 | 8개 필드를 매핑하고 숫자 문자열을 정수·범위 검증한다. 계산은 `bigint`, JSON은 문자열을 사용한다. | 필수 배열 누락이나 숫자 오류를 빈 결과로 바꾸지 않고 `502`. |
| 5. 저장 | 영화 upsert, 조회 기간과 실적 교체를 하나의 트랜잭션으로 처리한다. 정상 빈 결과도 짧은 TTL의 조회 기간 레코드로 구분해 저장한다. | 전체 롤백 후 `503`; 부분 저장 결과는 사용하지 않는다. |
| 6. 저장본 대조 | 저장 직후 동일 키를 JOIN 재조회해 건수, 영화 코드, 순위와 주요 수치가 정규화 결과와 일치하는지 확인한다. | 불일치나 재조회 실패는 `503`; 성공 응답으로 위장하지 않는다. |
| 7. 응답 | `data`와 `meta` DTO만 반환하고 내부 원문·비밀값은 제거한다. | 직렬화 불가능한 값은 `500`; `bigint` 자체를 JSON에 직접 넣지 않는다. |

동일 키에 대한 동시 캐시 미스가 발생하면 DB의 고유 제약과 트랜잭션으로 중복을 막는다. 필요하면 이후 단계에서 요청 병합이나 잠금을 추가하되, 중복 외부 호출 방지보다 데이터 정합성을 먼저 보장한다.

### 5.2 캐시 유효 기간과 제한 시간

| 항목 | 초기값 | 비고 |
| --- | --- | --- |
| 정상 결과 TTL | 1시간 | `expiresAt` 이전만 유효 |
| 정상 빈 결과 TTL | 5분 | 새 데이터 게시 가능성을 고려해 짧게 유지 |
| KOBIS 단일 요청 제한 시간 | 5초 | 초기 구현값. 실제 배포 측정과 KOBIS 정책에 따라 조정하며 변경 시 테스트·문서를 함께 갱신 |
| DB 단일 작업 제한 시간 | 3초 | 초기 구현값. 드라이버 지원 방식과 배포 측정 후 확정 |
| 인사이트 외부 동시 호출 | 최대 3개 | 7/14/30일 모두 동일하게 적용 |
| 내부 fetch 캐시 | 비활성화 | DB TTL이 단일 캐시 정책이 되도록 `no-store` 적용 |
| KOBIS fetch 캐시 | 비활성화 | DB 저장·만료 정책과 중복되지 않게 함 |

인사이트는 날짜별 일간 조회 파이프라인을 재사용한다. 분석 기간 중 하나라도 `502`, `503`, `504`로 실패하면 부분 결과를 성공으로 반환하지 않는다. 30일 요청의 전체 처리 제한 시간은 Vercel 실행 예산과 실제 측정 결과를 Phase 6에서 확인한 뒤 확정한다.

## 6. 구현 우선순위와 완료 기준

각 단계는 관련 검사 결과를 보고하고 승인을 받은 후 다음 단계로 진행한다. 필수 검사 실패나 미실행이 있으면 완료로 판정하지 않는다.

| 순서 | 우선순위 | 구현 범위 | 단계 완료 확인 기준 |
| --- | --- | --- | --- |
| 1 | 필수 | API 계약 타입, 입력 검증, 안전한 오류 DTO, KOBIS fixture 파서·숫자 정규화 | 정상·빈·본문 오류·잘못된 숫자·경계값 단위 검사가 통과하고 외부 서비스 없이 재현 가능 |
| 2 | 필수 | 실제 KOBIS 일간·주간·주말 어댑터, 타임아웃, `DATA_MODE=live` | 서버에서만 키를 사용하고 8개 필드 및 실제 집계 범위를 매핑하며 실패가 `502`/`504`로 구분됨 |
| 3 | 필수 | Supabase 마이그레이션, RLS, 트랜잭션 저장, JOIN, TTL 캐시, 저장본 대조 | 격리 DB에서 중복 방지·롤백·빈 저장·JOIN·만료 경계·대조 실패 검사가 통과함 |
| 4 | 필수 | 목록 내부 API와 F1 live 연결 | 한국 시간 전일 기본값, 여섯 필수 열, 일간/주간/주말, 검색 및 모든 상태가 실제 파이프라인에서 동작함 |
| 5 | 필수 | 인사이트 API 계산 로직 | 7/14/30일 합계·평균·빈 날짜 제외·동률 정렬·일부 실패 차단 단위 및 통합 검사가 통과함 |
| 6 | 필수 | F2 차트·Top 5/10·보조 지표와 상태 화면 | PRD의 인사이트 AC가 데스크톱·모바일 화면 검사에서 통과함 |
| 7 | 필수 | 전체 인수·보안·성능 검증과 운영 문서 | AC 1~16 통과, 비밀키 비노출, 30일 처리 시간 측정, 배포·되돌리기 절차 및 AC 17 사전 기록 완료 |
| 8 | 최종 | 승인된 Vercel·Supabase 환경에 배포 | 배포 URL에서 주요 흐름·오류·캐시 재사용이 검증되고 필수 실패·미실행 항목이 없음 |

초기 구현에서는 기능 범위를 넓히기보다 목록의 `live` 종단 흐름을 먼저 완성한다. 회원가입, 예매, 개인화, 흥행 예측은 범위에 포함하지 않는다.

## 8. 단계별 보고 형식

각 구현 단계 종료 시 다음을 구분해 보고한다.

- 변경 결과: 변경 파일, 구현 기능, 관련 PRD AC
- 통과: 실제 실행한 명령과 확인 결과
- 실패: 기대값, 실제값, 영향과 수정 계획
- 미실행: 실행하지 못한 검사와 필요한 조건
- 완료 판정: 해당 단계 완료 기준 충족 여부
- 다음 단계: 다음 작업 범위와 명시적 진행 승인 요청

파싱·숫자 정규화, DB 저장·캐시·JOIN, 매출·관객 지표 계산을 변경할 때는 `box-office-verification` Skill의 절차에 따라 결과를 `통과`, `실패`, `미실행`으로 구분한다.
